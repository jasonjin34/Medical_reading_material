# EXSCALATE: An extreme-scale in-silico virtual screening platform to evaluate 1 trillion compounds in 60 hours on 81 PFLOPS supercomputers

> **Bibkey** `Gadioli2021_211011644` · **Venue** arXiv preprint (2021) · **Category** drug-discovery · **Relevance** medium · **Access** open
> **Link** <https://arxiv.org/abs/2110.11644> · `status: complete`

---

## One-liner
This is a **software-engineering / HPC systems** paper: the authors rewrote Dompé's Exscalate docking platform as "one MPI process per node + an asynchronous in-node reader→splitter→docker→writer pipeline + heterogeneous CUDA/C++ workers", wrapped in a workflow (a decision tree predicts each ligand's docking time → ligands are bucketed by predicted time → ~3,400 independent SLURM jobs of ~5 minutes each). On CINECA-Marconi100 + ENI-HPC5 (81 PFLOPS combined) this docked **70+ billion** small molecules against **15 binding sites of 12 SARS-CoV-2 proteins** in **60 hours** — about **1 trillion** scoring evaluations at **5M ligands/s** across both machines (~2.2k ligands/s per node).

## Problem
Under "urgent computing" (a pandemic demands candidate drugs as fast as possible) the bottleneck in virtual screening is engineering, not chemistry: because molecules can be enumerated in silico from known reactions, library size is limited only by compute — and four of the top five TOP500 machines have GPU-heterogeneous nodes, so saturating them means solving a chain of systems problems: how to use accelerators efficiently, how to move data from storage into the node and feed the GPUs, how to minimise inter-node communication and process synchronisation, and how to stay resilient so a node failure does not discard completed work. The objective is blunt: **screen as many ligands as possible within a fixed time budget**.

## Method
**(1) The dock-and-score algorithm (four steps)**: ① ligand pre-processing — rotate torsional bonds to "flatten" the molecule, maximising the sum of internal inter-atomic distances (protein-independent, so precomputed once and reused across campaigns); ② dock into the binding site with a **greedy optimiser with multiple restarts**, driven by a scoring function considering **only geometric steric effects**, with ligand flexibility modelled and the pocket rigid — **256 initial poses per ligand** in the campaign; ③ cluster the generated poses at an **RMSD threshold of 3 Å**, putting each cluster's best pose first and sorting the rest by the geometric score; ④ re-score the **top 30 poses** with the **LiGen chemical scoring function**; the ligand's score is that of its best pose. Complexity is O(n·m) in atoms n and torsional bonds m; there are C++17 (CPU), OpenACC and CUDA implementations, CUDA fastest on NVIDIA GPUs. Measured per-ligand time spans **more than an order of magnitude** between the fastest and slowest ligand classes; the GPU version is insensitive to atom count (hardware parallelism) but sensitive to torsional-bond count (bonds must be processed serially to preserve geometry), with step increases at 64 and 96 atoms because work is organised in bundles of 32 atoms.
**(2) The high-throughput docking application**: a monolithic MPI application, **one process per node**, each spawning an asynchronous pipeline of C++11 threads — one dedicated thread per stage plus a thread-safe input queue: **reader** (sequentially reads chunks of the library file) → **splitter** (separates individual ligand descriptions) → **docker** (builds structures, docks and scores) → **writer** (accumulates SMILES + score in CSV-like form and flushes in batches). Only the docker stage may hold several threads **work-stealing** from the same queues, and it may mix CUDA and CPP workers to exploit node heterogeneity; several CUDA workers may be bound round-robin to one GPU. Pocket information is read once at start-up and kept resident (constant static memory for C++, texture memory for CUDA). The input file is partitioned **statically into equal slabs by file size and process count** (convention: a process handles every ligand whose description *begins* inside its slab, the last description may run past the slab end), keeping reads sequential and I/O-friendly — but static partitioning **removes work-stealing across MPI processes**, so application throughput equals that of the slowest process. The writer uses **collective I/O** to coalesce writes, with a configurable number of I/O-issuing processes to limit filesystem pressure. Stack: libdpipe (high-level MPI + C++ threads) + LiGenDock/LiGenScore (domain logic) + MPI/CUDA. It deliberately **does not rely on node-local storage** (unavailable on the target machines) — the key departure from the AutoDock-GPU/Summit route.
**(3) The Exscalate workflow (compensating for the application's weak points)**: instead of one giant machine-wide MPI job, launch **many small parallel jobs** via a plain SLURM/PBS job array. This buys two things — **fault resilience** (the default MPI response to a node failure is to terminate every process in the communicator, discarding large amounts of work; small jobs mean small re-runs) and **load balance** (large, complex ligands clustered together would badly slow the owning process). The flow: SMILES library → predict docking time with a **decision tree (max depth 16)** from features directly available at the SMILES level (heavy-atom count, ring count, chain count and their interactions) → bucket ligands at **10 ms** width → ligand pre-processing (add hydrogens, generate initial 3D coordinates, unfold — done once, reusable across campaigns) → emit custom binary ligand files → run the docking application over all ligand files **one pocket at a time** → one ranking of the library per site. After experts pick molecules binding strongly across several sites or proteins, the 3D pose can be **regenerated on demand** because the docking algorithm is **deterministic** — hence only SMILES + best score need storing. The workflow takes two kinds of domain input: the target proteins' binding sites (how to obtain them is explicitly out of scope) and the chemical library to evaluate.

## Data
**Targets**: 12 proteins / 15 binding sites covering the main functional units of the SARS-CoV-2 proteome, with crystal structures from the PDB (3CL protease/NSP5 = 6LU7, N-protein = 6VYO, NSP3 = 6W02, NSP9 = 6W4B, NSP12 = 7BV2, NSP13 = 6XEZ, NSP15 = 6W01, NSP16 = 6W4H, PL protease = 6W9C, Spike-ACE2 = 6M0J); **NSP6 uses a de novo model and NSP14 a homology model** (homology models were generated where no crystal structure existed). Pocket information totals only 29 MB, read once at start-up.
**Chemical library**: 70+ billion ligands. In SMILES it is **3.3 TB**; the docking application needs a richer description, so a custom binary format (atom positions, types, bonds only) replaces TRIPOS Mol2 (ASCII, readability-first), which would need **5–6× more space** — the binary library is **59 TB**. Storing every docked pose (15 sites × 30 re-scored poses per ligand) would require **26 PB**, so only SMILES + best score are kept, giving a **7.3 TB** final output (the conclusion instead says 64 TB; the discrepancy with §4.1's 7.3 TB is unexplained). **Tuning dataset**: "Commercial Compound MW<330" from the MEDIATE website, 5 million small molecules, publicly available. **Data for the time-prediction model**: measured docking times for 21 million ligands, 80% train / 20% test.
**Machines**: a Marconi100 node = 32-core IBM POWER9 AC922 (128 hardware threads) + 4× NVIDIA V100 with NVLINK 2.0; an HPC5 node = Intel Xeon Gold 6252 24C (24 cores / 48 hardware threads) + 4× V100, NVLINK only between GPUs; InfiniBand interconnect. Note: the opening of §4 states "70 million ligands", contradicting the 70+ billion of the abstract and conclusion — evidently a typo.

## Key results
- **Scale**: 60 hours on two machines totalling 81 PFLOPS, 70+ billion ligands × 15 binding sites ≈ 1 trillion dock-and-score evaluations — claimed as the **largest virtual-screening campaign to that date**.
- **Throughput**: **2.2k ligands/s** per node on average and **5M ligands/s** across both machines. Per site (Table 2): 2,427–2,499 ligands/s/node on Marconi100 (e.g. PLPRO 2,496; 3CL 2,427) for ~1.94–2.00M machine-wide; 1,965–2,010 on HPC5 for ~2.95–3.02M; NSP13ortho was split across both machines (2,454/1,987 per node). Machine throughput is wall-time-to-solution divided by library size, so it **includes all execution overheads**.
- **Heterogeneous-worker sweep (one Marconi100 node, Fig. 7)**: throughput peaks with a **high CUDA-worker count** (~2.4k ligands/s), while **raising CPP workers to match the hardware-thread count hurts** (664–985 ligands/s at 128 CPP workers). The conclusion: in this case study **CPUs are best used to support the accelerators and I/O rather than to compute**; and a single CUDA worker cannot saturate a GPU (it must parse the ligand description and initialise structures before launching kernels), so several workers are needed to hide that overhead.
- **Time-prediction model**: on 21 million ligands the decision tree has a **negligible mean error (−0.00088 ms) with a 3.81 ms standard deviation**; since per-ligand predictions still err, the workflow buckets at 10 ms to absorb the variance — load balancing only needs the average behaviour to be right.
- **Job decomposition**: the input was split into **~3,400 jobs**, each 32 MPI processes, ~5 minutes, targeting a single binding site; sites were evaluated **sequentially**. Per-node throughput at full-machine scale matches that measured during the worker sweep, i.e. the platform did exploit all available resources.
- **Public output**: the most promising compound set filtered per target was released on the MEDIATE portal so researchers worldwide can start finer de novo campaigns from a reduced set.

## Contributions
- **Replacing one giant MPI job with "a job array of small jobs + prediction-driven bucketing"**: a plain but effective design solving fault resilience and load balance at once — the cross-process work-stealing MPI cannot do is approximated at the scheduler level.
- **Treating docking time itself as a learnable quantity**: a decision tree over features available already at the SMILES level (heavy atoms, rings, chains) predicts runtime and drives bucketing — a clean, directly transferable cost model for campaign planning.
- **An in-node asynchronous pipeline with mixable CUDA/CPP workers**: saturates GPU-heterogeneous nodes without node-local storage, with the measured conclusion that CPUs should serve I/O and data feeding.
- **A deterministic algorithm ⇒ store "SMILES + best score" instead of poses**: shrinks a 26 PB storage requirement to 7.3 TB, regenerating poses on demand — a key "recompute rather than store" idea at extreme scale.
- **A compact custom binary ligand format**: 5–6× smaller than TRIPOS Mol2, bringing the full library to 59 TB.

## Limitations
- **The scientific output is not evaluated at all**: the paper is explicitly written from a software-engineering viewpoint and reports only throughput, storage and prediction error — **no enrichment, no hit rate, no recovery of known actives, no in vitro validation**. The "most promising compounds" were selected by domain experts after ranking, and neither the criteria nor the outcome appear here.
- **A very coarse scoring function**: search is driven by a purely steric geometric score, the pocket is rigid, and only the top 30 poses are re-scored — a deliberate accuracy trade-off for throughput whose cost is never quantified (e.g. against AutoDock-class methods).
- **Static data partitioning removes cross-process work stealing**, pinning throughput to the slowest process; bucketing only partly mitigates this (the 3.81 ms per-ligand standard deviation remains).
- **One pocket at a time, sites evaluated sequentially**, so the library is swept 15 times in full; there is no adaptive mechanism to decide where further compute should go — all 7×10¹⁰ ligands were docked against all 15 sites.
- **Reproducibility is out of reach**: it needs two top European supercomputers and a 59 TB input; Exscalate/LiGenDock/LiGenScore are Dompé's proprietary stack and no code link is given.
- **Internal inconsistencies**: output size 7.3 TB (§4.1) vs 64 TB (conclusion); library size written as "70 million" at the start of §4. Prefer the abstract/conclusion's 70+ billion and §4.1's itemised figures, and flag this when citing.

## Relation to our direction
For the Hayat-lab (Uniklinik Aachen) project "**Autonomous scientific orchestration of virtual screening**" (LLM agents + molecular foundation models + docking + active learning, planning/executing/improving campaigns from protein structures to find suitable compounds), this paper is the **ceiling reference for the layer being orchestrated** — and the best argument for why orchestration is needed at all.
- **It is the exhaustive baseline our adaptive pipeline must beat.** EXSCALATE docked 7×10¹⁰ ligands against 15 sites by brute force on 81 PFLOPS; the entire value proposition of active-learning screening is reaching a comparable top-k at a small fraction of that compute. That gives a clean **comparison axis**: on a fixed library/target, "top-k from exhaustive docking" is the ground truth for an agent pipeline, and the **compute-to-recall curve** (docking calls spent vs top-k recovered) is the metric.
- **The runtime-prediction model drops straight into the agent's planner.** A planning agent must answer "how long will this batch of 10⁶ molecules take on this pocket, and does it fit the budget?" The decision tree here (heavy atoms / rings / chains → docking milliseconds, mean error ≈ 0, σ = 3.81 ms) is exactly that **cost model**, and it needs only SMILES, no 3D pre-processing — ideal for a planner deciding whether to expand a batch. Bucketing by predicted time, and absorbing prediction error at 10 ms granularity, transfer directly to our batch scheduling.
- **Treating docking as an orchestratable tool needs precisely these engineering contracts.** The one-pocket job granularity (~5 min × 32 processes) is a natural **action unit** an agent can launch, cancel and retry; a deterministic algorithm plus "store only SMILES + score, regenerate poses on demand" gives the agent a very cheap state representation (no tens of TB of poses in its memory); and the small-job-array fault semantics mean a mid-campaign failure does not restart everything. These are conventions to copy when designing our docking tool interface.
- **Multiple sites / proteins are a natural agent decision space.** The paper prepares 15 sites over 12 proteins, with NSP6 from a de novo model and NSP14 from a homology model — exactly our "given protein structures" setting, with uneven structural quality. It treats all sites sequentially and equally; an orchestrator's job is to be **unequal**: allocate further compute by structural confidence (de novo/homology vs crystal) and early hit enrichment, decide whether to switch sites, or to run a structure prediction first. Pocket identification is explicitly out of scope here, whereas in our pipeline it should be the agent's first step.
- **It also sets the bar we must clear.** EXSCALATE reports no scientific metric, so it cannot be cited for "bigger is better"; conversely, an agent pipeline claiming to beat brute force must supply what is missing here — enrichment/hit rate, recovery of known actives, and an error-propagation analysis for the coarse scoring (steric score + rigid pocket). Reading it against `competitive-docking-npjdrugdiscov-2026` is instructive: that work quantifies ranking–experiment agreement with co-folding models across ~17 systems (c-index 0.52–0.89) but handles only hundreds of ligands. The two mark the cheap-and-coarse and expensive-and-accurate ends of our scoring ladder, and the **cascade decision** between tiers (which scorer first, when to escalate, when to abandon) is the orchestrator's central job.

## Follow-ups
- The billion-molecule AutoDock-GPU campaign on Summit (LeGrand et al. 2020; Glaser et al., *IJHPCA* 2021), the paper's closest comparator: node-local NVMe, FireWorks orchestration, RFScore-VS re-scoring, BlazingSQL statistics — **its orchestration layer is closer to an agent-drivable workflow** than Exscalate's and deserves a read from the tool-interface angle.
- Gervasoni et al., *IJMS* 2020 (Pockets 2.0, a comprehensive mapping of druggable cavities in SARS-CoV-2 proteins): the paper puts "how to obtain binding sites" out of scope, yet that is our pipeline's first step.
- Beato et al. 2013 (LiGenDock's scoring function and design-of-experiments tuning) and Vitali et al., *J. Supercomput.* 2019 / PBio 2018 (OpenACC/OpenMP acceleration of the same geometric docking method): needed to judge how coarse the "steric + rigid pocket" tier really is.
- Rocco et al., *J. Supercomput.* 2021 (Legio: fault resilience for embarrassingly parallel MPI applications) — the fault-semantics reference if our orchestrator manages MPI-level jobs rather than just submitting job arrays.
- Did EXSCALATE4CoV publish a **scientific-outcome** paper (which compounds were validated in vitro/in vivo)? Nothing here reports it, and the answer decides whether this can serve as a reference for the scientific yield of exhaustive screening.
